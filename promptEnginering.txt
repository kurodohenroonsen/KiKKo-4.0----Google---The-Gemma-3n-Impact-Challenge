#### Introduction

Creating a robust single-call prompt for an on-device Large Language Model (LLM) to generate a kid-friendly "AI Overview" from ambiguous image analysis data is a complex task. The input data, derived from computer vision models like Google’s ML Kit, includes a main subject guess, OCR results, object detection results, and classification labels with confidence scores. These inputs can be contradictory, leading to LLM failures such as misinterpreting context, ignoring instructions, or producing low-quality content. The proposed prompt template addresses these challenges using advanced prompt engineering techniques to ensure accurate subject identification and high-quality, structured output.



#### Problem Analysis

The observed LLM failures include:

- **Contextual Misinterpretation**: The LLM may focus on a single data point (e.g., "Bridge" in OCR) and generate incorrect content (e.g., about a physical bridge), ignoring other clues like "Rice Vinegar" or "Condiment."

- **Ignoring Negative Instructions**: The LLM often disregards commands like "DO NOT describe the image itself."

- **Subject Hijacking**: When provided with a few-shot example (e.g., about a muffin), the LLM may generate content about the example’s subject instead of the actual input’s subject (e.g., a crêpe).

- **Low-Quality Content**: Outputs may include generic or factually incorrect "fun facts" or unsafe procedural steps.



To address these, the prompt must guide the LLM to synthesize contradictory inputs, adhere to instructions, and produce engaging, accurate content for kids.



#### Prompt Design

The proposed prompt template is structured to maximize clarity, enforce reasoning, and ensure high-quality output. Below is a detailed breakdown of its components and the techniques used.



##### Prompt Components

| Component | Description |

|-----------|-------------|

| **Persona Definition** | The LLM is defined as "KidSmart," a friendly, educational AI assistant for kids, setting the tone for engaging and age-appropriate content. |

| **Input Data Format** | The input data is structured with clear labels (e.g., `[MAIN SUBJECT IDENTIFIED]`) and enclosed in triple backticks to separate it from instructions. |

| **Reasoning Step** | The LLM is instructed to analyze all input data, weigh evidence, and resolve contradictions before generating the overview. |

| **Few-Shot Example** | An example overview for a muffin is provided to illustrate the desired format and style, with explicit instructions to avoid using its subject. |

| **Output Structure** | The prompt mandates a specific Markdown structure with sections like `# Title`, `## Fun Facts`, and `## Questions to Think About`. |

| **Guidelines** | Explicit rules ensure factual accuracy, kid-friendliness, and adherence to negative instructions (e.g., not describing the image). |



##### Techniques Used

1. **Chain of Thought / Reasoning Steps**  

   The prompt requires the LLM to first analyze the input data and determine the most plausible main subject. By explicitly instructing the LLM to weigh all data points (e.g., OCR, classifications) and resolve contradictions, it prevents misinterpretations like fixating on "Pearl River Bridge" when "Rice Vinegar" is the correct subject. This step-by-step reasoning reduces the risk of hallucination and ensures the LLM bases its output on a synthesized understanding of the data.



2. **Delimiters and Structure**  

   Clear labels and triple backticks (` ``` `) separate the input data from instructions, making it easy for the LLM to parse. This structure minimizes confusion, especially with noisy inputs like OCR results, and ensures the LLM processes the data systematically.



3. **Persona Reinforcement**  

   The persona "KidSmart" is defined to align the LLM’s tone with the goal of creating engaging, educational content for kids. This helps maintain consistency and ensures the output is approachable and fun.



4. **Few-Shot Example Placement**  

   The few-shot example (about a muffin) is placed after the reasoning instructions and clearly marked as an example for format and style, not content. Explicit instructions prevent the LLM from generating content about the example’s subject, addressing the subject hijacking issue.



5. **Forced Output Formatting**  

   The prompt specifies a strict Markdown structure, reinforced by the example. This ensures the output is consistently formatted, making it easy to read and integrate into the mobile app.



6. **Negative Instructions**  

   The prompt explicitly states, "Do not describe the image itself," to enforce adherence to this critical rule. By reiterating this, the LLM is less likely to deviate from the task.



7. **Quality Control**  

   Guidelines like "Ensure all information is factually accurate and appropriate for kids" and "Omit uncertain information" prevent low-quality or unsafe content. This addresses issues like generic facts or dangerous procedural steps.

Explanation of Techniques Used

Chain-of-Thought Reasoning: The prompt explicitly instructs the model to “think through each piece of evidence step-by-step” and to state the conclusion before answering. This forces the model to use intermediate reasoning rather than jumping to an answer.  In practice, adding instructions like “explain your answer step-by-step” is known to improve complex reasoning in LLMs. By guiding the model to weigh all clues (OCR, objects, labels) logically, we avoid it latching onto one misleading cue.

Structured Prompt with Delimiters: We divide the prompt into clear sections (e.g. <INSTRUCTIONS>, <EXAMPLE>, <INPUT_DATA>, <ANALYSIS>, <FINAL>).  This “Instruction, Context, Input, Output” structure helps the model parse what to do.  For example, the example block shows the entire reasoning format, and the actual input block is clearly separated. Using labeled sections and placeholders makes it clear which text is instruction, which is example or input, and where the model’s response should go.

Persona and Style Guidance: The model is given a strong persona (“friendly, kid-friendly AI assistant”) and tone guidelines (clear, simple language; avoid jargon or complex terms). System prompts or instructions can shape an LLM’s tone and style.  By stating things like “explain the subject in simple Markdown” and “avoid technical words,” we ensure the answer is age-appropriate. We also include explicit do’s and don’ts (e.g. “Do NOT just describe the image” or “no recipes”), which keeps the model focused on the task and less likely to stray into irrelevant or disallowed content.

Enforced Output Format: We explicitly tell the model how to format the answer: use Markdown headings and bullet points. For example, we start the answer with # {SubjectName} as a level-1 title and use lists for facts. This acts as an output indicator, similar to using a label like “Answer:”. By demonstrating the exact output in the example (heading, paragraphs, bullets), the model learns the required structure.  Citing example output format helps ensure consistency (as noted in prompt-guides, keeping a fixed format aids performance).

Few-Shot Example for Formatting: We include one illustrative example (inside <EXAMPLE>) showing how to analyze the clues and produce the markdown answer. Providing a demonstration in the prompt helps the model learn the pattern of reasoning and output (few-shot in-context learning). This example is clearly marked and separated so the model treats it as guidance rather than as the actual input. In the instructions we can even say “do not confuse the example subject with the new one” to prevent subject hijacking. The example ensures the model sees a correct chain-of-thought and final answer format, which improves its performance on the real input (as few-shot prompting guides models towards the desired style).

Chain of thought prompting transforms multi-modal reasoning performance

Multi-modal chain-of-thought (CoT) prompting represents the most significant advancement in handling complex visual-textual reasoning tasks. Academic research from 2024-2025 demonstrates that proper CoT implementation can achieve 85.31% accuracy on complex reasoning benchmarks, outperforming much larger models.

The key innovation lies in two-stage processing: first generating intermediate reasoning steps based on multi-modal information, then leveraging these rationales for final answer generation. This approach proves particularly effective for on-device deployment because it explicitly handles uncertainty and contradictions that commonly occur in computer vision outputs.

Compositional chain-of-thought (CCoT) extends this further by using scene graphs as intermediate representations. This technique generates a structured representation of visual elements and their relationships, then uses this graph for detailed reasoning. Research shows 15-20% improvement over baseline multi-modal models when handling complex visual scenes.

Visual analysis - identify objects, text, and scene elements

Synthesis - generate final response with confidence indicators

A Framework for Robust Multimodal Reasoning in On-Device LLMsIntroduction: A Framework for Robust Multimodal ReasoningThe challenge of developing reliable artificial intelligence systems for on-device applications lies not only in managing computational constraints but also in ensuring robust reasoning, especially when faced with ambiguous or conflicting inputs. The observed failures—contextual misinterpretation, instructional negligence, subject hijacking, and the generation of low-quality content—are not isolated bugs. Rather, they represent a systemic breakdown of in-context reasoning under multimodal ambiguity. This is a well-documented phenomenon where models struggle to align and synthesize information from different modalities, such as text and vision, leading to unreliable or hallucinatory outputs.1 An AI system for a self-driving car misidentifying a crowded intersection as clear is a high-stakes example of this same fundamental problem: a failure to correctly weigh conflicting signals from different data streams.1The core strategy to overcome these challenges is to move beyond simplistic, direct instruction and adopt a structured, multi-stage reasoning framework within a single prompt. This report proposes a two-part prompt architecture that enforces a "reasoning-then-generating" cognitive sequence. The first part of the prompt compels the Large Language Model (LLM) to conduct a private, internal analysis of the provided multimodal evidence, weigh its reliability, resolve contradictions, and explicitly declare a definitive conclusion. Only after this internal reasoning is complete does the second part of the prompt guide the LLM to use that conclusion to generate the final, user-facing output. This methodical decomposition is directly inspired by advanced prompting techniques like Multimodal Chain-of-Thought (MCoT) and Plan-and-Solve (PS) prompting.2 These methods improve the reliability of LLMs on complex tasks by breaking down a single, difficult problem into a series of smaller, more manageable logical steps, thereby enhancing transparency and reducing errors.6This structured approach is particularly critical for on-device models. With fewer parameters compared to their cloud-based counterparts, local LLMs have a diminished capacity to disambiguate poorly structured or underspecified prompts.8 For these models, a highly structured and explicit prompt is not merely a best practice but a fundamental necessity for reliable performance. The proposed framework effectively offloads a significant portion of the cognitive load from the model's internal weights onto the explicit structure of the prompt itself, guiding the model through a logical process that it might otherwise fail to discover on its own.The Foundational Architecture: Structuring the Prompt for Clarity and ControlThe architecture of a prompt is as crucial as its content. For an LLM to navigate complex, multi-part instructions with conflicting data, the prompt must be structured to eliminate ambiguity and prevent different contextual elements from interfering with one another. This requires a deliberate design that guides the model's attention and processing flow in a predictable manner.The Primacy of Semantic Delimiters: Why XML is SuperiorTo achieve the necessary level of structural clarity, the use of semantic delimiters is paramount. While simple separators like --- or ### can provide some structure, XML-style tags (e.g., <input_data>, <instruction>) are demonstrably superior for complex prompting tasks. Research and best practices from leading AI labs confirm that semantically meaningful tags provide clearer structural and contextual cues to the model, a practice sometimes referred to as "context engineering".10LLMs are trained on vast corpora of text from the internet, which includes immense amounts of structured data like HTML and XML. Consequently, they have learned to recognize the hierarchical and descriptive nature of these tags.10 Using XML tags effectively creates a "prompt grammar" that the model can parse robustly. This structure helps prevent "context contamination," a phenomenon where the model erroneously blends information from different parts of the prompt, such as instructions, examples, and input data.10 This contamination is the direct mechanism behind the observed "subject hijacking" and "contextual misinterpretation" failures. By creating hard, unambiguous boundaries between different prompt components, XML tags ensure that the model understands the distinct role of each piece of information, which is essential when processing complex inputs.14A Proposed Hierarchical Structure: The Tripartite PromptThe proposed prompt architecture is organized into a tripartite structure, with three main top-level XML sections designed to manage the cognitive workflow of the LLM. This structure deliberately mirrors a logical human problem-solving process: first, understand the overall rules; second, analyze the specific evidence; and third, formulate the final response. By enforcing this sequence, the model's internal process becomes more transparent and controllable, which is a key benefit of Chain-of-Thought (CoT) style prompting.16 The current failures stem from the LLM attempting to reason and generate content simultaneously, leading to confusion and error. Advanced prompting techniques like Plan-and-Solve and ReAct demonstrate the power of separating the planning or reasoning phase from the acting or generation phase.3 This tripartite structure simulates that separation within a single prompt call.The three core modules are:<SYSTEM_INSTRUCTIONS>: This is a global configuration block placed at the very beginning of the prompt. It contains the foundational elements that govern the model's behavior throughout the entire task. This includes the detailed persona the LLM must adopt, the overarching rules of engagement, and a set of explicit negative constraints that function as safety guardrails. Information in this block has global scope within the prompt.<REASONING_MODULE>: This is a self-contained "scratchpad" where the LLM is instructed to perform its evidence synthesis. The model is guided to work through a series of analytical steps, weigh the conflicting data, and arrive at a definitive conclusion. Crucially, the output generated within this module is for the model's internal use only and is explicitly forbidden from appearing in the final user-facing response. This forces the model to reach a conclusion before it begins the creative writing process, preventing the kind of on-the-fly misinterpretations that were observed.<GENERATION_MODULE>: This is the final stage of the prompt. Here, the LLM is instructed to take the firm conclusion it declared in the <REASONING_MODULE> and use it as the sole basis for generating the polished, kid-friendly Markdown output. It establishes a clear, sequential workflow—analyze first, then write—that directly mitigates the risk of contextual misinterpretation and ensures that the final creative output is grounded in a deliberate and explicit reasoning process.The Reasoning Module: Forcing Evidence-Based SynthesisThe core of the solution lies within the <REASONING_MODULE>, which is designed to tackle the primary challenge of synthesizing ambiguous and contradictory multimodal data. This module implements a form of Multimodal Chain-of-Thought (MCoT) prompting, forcing the LLM to externalize its reasoning process in a step-by-step manner.8 This makes the model's "thinking" auditable and guides it toward a more logical conclusion when faced with conflicting signals from sources like OCR and image classifiers.1Step 1: Evidence Triage and Reliability WeightingThe first instruction within the reasoning module directs the LLM to perform an evidence triage. This gives the model a clear protocol for resolving the exact type of conflict described in the user's problem statement, guiding it to handle contradictory information effectively.7Step 2: Hypothesis Generation and Contradiction ResolutionOnce the evidence is triaged and weighted, the prompt guides the model to form a primary hypothesis.
